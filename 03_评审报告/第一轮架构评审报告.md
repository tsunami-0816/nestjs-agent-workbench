## 发现问题

### P0（致命）

**无。** 无技术选型硬冲突、无核心链路完全中断、无数据一致性风险。

### P1（核心链路部分异常，需在第二轮定稿补齐）

**P1-1：CORS 未配置**
- 问题描述：dev 模式下前端 Vite 在 5183，后端 NestJS 在 8089，跨域请求会被浏览器拦截。架构文档 main.ts 启动流程没写 `app.enableCors()`。
- 影响：前端 axios 在 dev 模式下直接调不通后端，step6 冒烟第一关就卡住。
- 建议：在 §6 部署架构或 main.ts 启动流程里补 `app.enableCors({ origin: ['http://localhost:5183'], credentials: true })`；生产模式下 nginx 同源代理不需要 CORS。

**P1-2：登出后已建立的 WebSocket 长连接未主动断开**
- 问题描述：M5 要求"登出后旧 token 立即失效"。但 WebSocket 是长连接，握手时已经鉴权通过；登出只加了 HTTP 层 Redis 黑名单，已建立的 WS 连接仍然活着，用户还能继续发消息收到流式回复。这违反 M5。
- 影响：M5 指标验收时，登出后用已开着的 WS 连接发消息，后端仍然会调 DeepSeek 并推送——token 黑名单只挡 HTTP 不挡 WS。
- 建议：ChatGateway 维护一个 `Map<userId, Set<WebSocket>>`（连接时 add，断开时 delete）；AuthService.logout 时调 ChatService 找到该用户的所有 ws 连接并 close(4001)。这样登出后 HTTP 和 WS 同时失效。

**P1-3：WebSocket 流式调用中途客户端断开未 abort 大模型流**
- 问题描述：用户发消息后立刻关页面/断网，DeepSeek 的 stream 还在被 for await 读取，会持续消耗 API 额度直到流自然结束。架构没写断线清理。
- 影响：不是功能 bug，但是资源浪费，面试讲"流式对话生命周期管理"时这是个明显遗漏。
- 建议：ChatGateway 监听 `handleDisconnect`，从活跃流 Map 里取出对应 AbortController 调 `.abort()`；ChatService.streamChat 接收一个 signal 参数传给 openai SDK。

### P2（非核心，记入 backlog 不阻塞）

**P2-1：对话标题不自动更新**
- 创建对话时 title 默认"新对话"，首条用户消息发完后应该把 title 改成消息前20字。当前架构没写。不阻塞 MVP，但体验好一点。
- 建议：第二轮定稿在链路 B 步骤里加一句"首条消息后 UPDATE conversations SET title=LEFT(content,20)"。

**P2-2：POST /conversations 创建新对话时 Redis 缓存未失效**
- 链路 B 只在 assistant 消息写完后失效缓存，创建新对话时也应该 del `conv:list:<userId>`，否则用户新建对话后 5 分钟内列表看不到新对话。
- 建议：ConversationService.create 末尾 `redis.del('conv:list:' + userId)`。

**P2-3：nginx.conf WebSocket 代理头配置未明确写**
- §6 风险表里提了 proxy_buffering off，但部署架构里没给 nginx.conf 的关键配置。开发时容易漏写 Upgrade/Connection 头导致 WS 连不上。
- 建议：第二轮定稿在 §6 补一段 nginx.conf 示例（location /ws { proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; proxy_http_version 1.1; }）。
