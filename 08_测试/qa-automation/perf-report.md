# 性能测试报告（2026-11-08）

## 测试环境
- 目标接口：`GET /health`（纯内存，不查 DB/LLM，排除外部依赖）
- 后端：NestJS dev 模式（`nest start --watch`），Node 22 单进程
- 压测脚本：`perf_test.py`（Python 多线程）
- 持续时长：每档 10 秒

## 压测数据

| 并发 | 总请求 | 平均 RT (ms) | P95 RT (ms) | TPS | 错误率 |
|---|---|---|---|---|---|
| 10 | ~6500 | ~7 | ~12 | ~650 | 0.00% |
| 20 | 13025 | 15.5 | 26.1 | 1302.5 | 0.00% |
| 50 | 13281 | 38.6 | 67.1 | 1328.1 | 0.00% |

## 瓶颈分析

1. **TPS 拐点**：20→50 并发 TPS 从 1302 涨到 1328（仅 +2%），但 RT 从 15.5ms 涨到 38.6ms（+150%）。典型的"TPS 不涨、RT 线性上升"——Node 单线程事件循环饱和。
2. **瓶颈定位**：NestJS dev 模式下 Node 主线程是瓶颈，不是 DB 连接池（/health 不查库）。生产环境 `node dist/main.js` 去掉 watch 后会有提升。
3. **调优建议**：
   - 生产部署用 PM2 cluster 模式（`pm2 start -i max`），利用多核
   - 反向代理层（nginx）做连接复用
   - DB/LLM 密集型接口需要单独压测（本报告只覆盖内存接口）

## 结论
- 内存接口 TPS ~1300，P95 < 70ms，对 MVP 项目足够
- 0 错误率
- JMeter 交叉验证：本机未装 JMeter，Python 数据已足够说明量级（deferred 到 step9 运维阶段）
